# 交易与网站性能优化设计

## 目标

在不改变业务功能或数据一致性承诺的前提下，缩短交易页面首次加载、交易新增/修改后的确认等待，以及状态页的搜索与操作等待。界面只能在飞书确认写入、并且应用已重新读到飞书最新数据后显示成功。

## 现状与根因

- 交易页首次加载分别请求交易列表和本月汇总；两者都要读取同一张飞书多维表格。
- 新增、编辑、删除和批量操作完成后，页面会使交易列表与汇总失效并等待二者重新请求；状态页还会额外刷新状态列表。这产生多个前端请求和重复的服务端工作。
- 自用、待收货、在售页面的搜索在每个键入事件后立即查询，连续输入会发起多次完整飞书读取。
- 前端的路由与 Excel 导出已经按需加载。生产构建仍输出 source map，增加部署文件体积但不带来用户运行时收益。

## 方案

### 统一的交易工作区读取

后端增加一个只读工作区接口。它在一次 `listRecords` 调用中：

1. 映射飞书记录和字段告警；
2. 按当前筛选、分页、排序计算交易列表；
3. 按本月范围计算汇总；
4. 返回列表、汇总和告警。

交易页将列表和本月汇总改为一个 React Query。页面初始加载只发起一次工作区请求。请求失败时保留既有错误展示和重试能力。

### 严格的写后回读

所有会改变交易数据的操作保持以下顺序：

```text
提交写入 → 飞书成功响应 → 统一工作区接口重新读取飞书 → 原子更新本地查询缓存 → 显示成功
```

不会使用乐观更新、跨请求持久缓存或以写入响应替代重新读取。飞书读取失败时，操作被视为未完成：编辑抽屉保持打开，列表和汇总不更新，并显示错误，供用户重试。这样能保证成功提示出现时，当前页面已经展示飞书最新值。

交易页将以回读返回的数据一次性写入相关 React Query 缓存；不再通过多个 `invalidateQueries` 触发并行但重复的网络请求。状态页的写后刷新也复用统一的回读结果，并仅更新实际受影响的列表/汇总缓存。

### 输入与交付优化

- 状态页的搜索使用约 250 ms 的防抖值作为请求键；输入中保留已有结果，停止输入后才请求，清空搜索立即请求。
- 保持路由懒加载和 Excel 导出动态导入，避免把分析图表或导出库纳入交易页初始包。
- 生产构建关闭浏览器 source map，以缩小部署产物；TypeScript、lint、单元测试和生产构建仍作为发布验证。

## 测试与验收

- 后端测试证明工作区接口只调用一次飞书记录读取，并同时返回筛选后的列表和月度汇总。
- 页面测试证明首次交易页只调用一次统一读取；保存后先写入、再进行恰好一次回读，且在回读完成前不关闭抽屉或显示成功。
- 状态页测试证明快速连续输入只触发一次最终搜索请求，且写后仍严格回读。
- 运行完整测试、类型检查、lint 和生产构建；比较构建输出以确认 source map 不再进入生产产物。

## 非目标

- 不改变飞书字段、财务计算、页面布局或用户权限。
- 不引入 Cloudflare KV、Durable Object、第三方监控或新的云端付费资源。
- 不修改未涉及交易读取/写入的页面行为。
